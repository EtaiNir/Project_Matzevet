# סוכן העיבוד — התקנה על המחשב של סבא

> ## ⚠️ הסוכן במחשב של סבא מפגר אחרי הקוד
>
> הגרסה בשרת יודעת **מצב"ת בלבד**. שני ענפים נבנו אחריה ו**טרם הותקנו שם**:
>
> - **דרג ב' (גנים)** — 16–27.9.2026. עד שיותקן, הגנים מעובדים בסוכן
>   פיתוח במחשב של אייל (`worker.py --tier-b-only`). מחשב כבוי = קליטה ממתינה.
> - **סבב בגרות** — 5.10.2026. תור `bagrut_uploads` (מיגרציה 027).
>
> **מה להעתיק לשרת:**
>
> | קובץ | למה |
> |------|-----|
> | `agent/worker.py` | ענפי דרג ב' ובגרות, הדגל `--tier-b-only`, ופלט ב-UTF-8 |
> | `scripts/load_tier_b.py` · `tier_b_fields.py` · `tier_b_catalog.py` · `gen_tier_b_catalog.py` | קליטת הגנים |

> **ובנוסף:** `ANTHROPIC_API_KEY=` ב-`.env.agent` (לזיהוי השדות בגנים).
> לבגרות אין צורך במפתח ולא ב-`pyodbc` — הסוכן קולט מאקסל.
> אחרי ההעתקה: עדכון גרסה (למטה), ואז לכבות את סוכן הפיתוח אצל אייל.
>
> המיגרציות (023–027) כבר הוחלו על המסד המשותף — שם אין מה לעשות.

הסוכן רץ ברקע 24/7 ומזין את המערכת משני מקורות:

```
א.  האתר → העלאה ל-Storage → [ הסוכן ] → pipeline → Supabase
     (בדיקה כל 5 שניות)

ב.  תיקייה מקומית שאליה מגיעים קובצי משרד החינוך
     → [ הסוכן ] → pipeline → Supabase
     (סריקה כל דקה)
```

בשני המקרים: גיבוי הטבלה הקיימת, ואז טעינה. הכול מתועד ב-`moe_uploads`
ונראה באתר במסך **נתוני המועצה → היסטוריית עדכונים**.

ועוד שני תורים מהאתר, באותה לולאה:

| תור | מקור | זרימה |
|---|---|---|
| `tier_b_uploads` | כפתור «⬆ גנים» | זיהוי שדות → **אישור באתר** → טעינה |
| `bagrut_uploads` | מודול הבגרות → «קליטת סבב» | בדיקה וטעינה בריצה אחת — **בלי אישור** |

## סבב בגרות

המבנה קבוע וידוע מראש — T1, T2 והמצפן — ולכן הוא בנוי כמו המצב"ת ולא כמו
הגנים: `pending` → `processing` → `done` / `failed`
([החלטה 014](../docs/decisions/014-bagrut-module.md)).

1. מוריד את הקבצים מ-`moe-uploads/{code}/bagrut/{stamp}/`. שם הם נקראים לפי
   תפקיד (`details.xlsx`, `t1_11.xlsx`, `t1_13_1.xlsx`, `t2.xlsx`,
   `compass.xlsx`) — Storage פוסל עברית (מלכודת 31).
2. מחזיר לכל קובץ שם עברי ("זכאות 11 …") — כך `load_bagrut.py` מזהה אותם.
3. מריץ `load_bagrut.py --report-json`. **שגיאה** (סמל מוסד שאינו תואם, קובץ
   חסר, קלט ריק) עוצרת לפני כל שינוי במסד → `failed` עם הודעה קריאה.
   **אזהרה** (משקלים שאינם 100%, שאלונים יתומים) — נטען, והאזהרה נשמרת
   ב-`report` ומוצגת בהיסטוריה באתר.
4. מוחק את התיקייה הזמנית — הקבצים מכילים ת"ז וציונים.

קליטה חוזרת של אותו מוסד, מועד ושנה מחליפה את הסבב. **סימוני המעקב של
הצוות נשמרים** — הם לפי בית ספר + ת"ז, לא לפי סבב.

| קובץ | מתי |
|---|---|
| **`run-once.bat`** | בדיקה — סבב אחד (תיקייה + אתר) ויציאה |

- מרימה את עצמה אם התהליך נופל (עד 999 פעמים, כל דקה)
- רצה בלי חלון (`pythonw.exe`) ולא מפריעה לעבודה

## תיקיית המצב"ת המקומית

אם קובצי משרד החינוך מגיעים אוטומטית לתיקייה על המחשב, מוסיפים ל-`.env.agent`:

```
MATZEVET_WATCH_FOLDER=D:\מצבת\נכנס
```

### ההפעלה הראשונה לא מעבדת כלום

התיקייה אצל סבא מתעדכנת כל חודש כבר שבע שנים. בסבב הראשון מול תיקייה
שלא נראתה קודם הסוכן **רושם מה כבר יש בה ויוצא**:

```
חיבור ראשון לתיקיית המצב"ת: D:\מצבת\נכנס
נרשם מצב פתיחה — 3 רשויות. הקבצים הקיימים *לא* יעובדו.
מכאן ואילך יעובד רק מה שיתעדכן בתיקייה.
```

בלי זה, עצם החיבור היה מפעיל טעינה לכל מועצה שיש לה קבצים שם — עדכון
המוני שאיש לא ביקש. גם החלפת התיקייה נחשבת חיבור חדש.

לעבד בכל זאת את מה שכבר בתיקייה:

```powershell
venv\Scripts\python.exe worker.py --once --process-existing
```

הדגל מתעלם ממצב הפתיחה ומהמעקב, ולכן טוען לכל מועצה את הקבצים העדכניים
שנמצאו — שימושי כשמחברים מועצה חדשה, מסוכן בכל מצב אחר.

### מה קורה בכל סבב

מה שהסוכן עושה כל דקה:

1. סורק את התיקייה ומקבץ את קובצי ה-CSV **לפי קוד הרשות**
2. מדלג על מועצה שחסרים לה קבצים (צריך את כל השישה)
3. מדלג על קבצים שנגעו בהם בחצי הדקה האחרונה — הם עדיין בהעתקה
4. בוחר לכל מועצה את **הקובץ העדכני ביותר מכל סוג**, ומתעלם מהשאר
5. מעבד רק מועצה שהקבצים שלה **באמת השתנו** מאז הפעם הקודמת

קבצים ישנים יכולים להישאר בתיקייה — אין צורך לנקות אותה.

רשות שנוספה למערכת *אחרי* רישום מצב הפתיחה אינה מכוסה בו, ולכן הקבצים
שלה ייטענו בסבב הבא. זו הכוונה: כך מועצה חדשה נטענת מעצמה.

### לפי מה נקבע "העדכני ביותר"

לפי **חותמת הזמן שמשרד החינוך שם בשם הקובץ**, לא לפי `mtime` בדיסק:

```python
def file_version(path):
    # (יש חותמת, החותמת, mtime כשובר שוויון)
```

`robocopy /COPY:DAT`, חילוץ מ-ZIP וכלי סנכרון משמרים את תאריך המקור. קובץ
שהגיע היום יכול לקבל `mtime` ישן מזה של קובץ שהועתק לתיקייה בחודש שעבר —
ואז בחירה לפי `mtime` הייתה טוענת נתונים בני חודשיים על גבי העדכניים,
בשקט. השם אינו משתנה בהעתקה.

### איך הוא יודע לאיזו מועצה שייך כל קובץ

לפי **מילה שלמה** בשם הקובץ, מול `moe_code` של הרשות:

```
TALMIDIM_AM_2026_1400000_2026-06-18-19-02-11_from_moe.csv
                 ↑ קוד הרשות
```

ההתאמה על מילה שלמה ולא על הכלה — אחרת קוד קצר כמו `120` היה נתפס
בטעות בתוך חותמת תאריך. מועצה שאינה במערכת פשוט מדולגת.

### למה הקבצים מועתקים לתיקייה זמנית

ה-pipeline בוחר קובץ לפי קידומת מתוך התיקייה שנתנו לו. אם בתיקייה יש
כמה מועצות, הוא היה מערבב ביניהן. לכן הסוכן מעתיק את ששת הקבצים של
המועצה הנוכחית לתיקייה נפרדת, ומוחק אותה בסיום.

### מעקב

מה כבר עובד נשמר ב-`watch-state.json`:

```json
{
  "version": 2,
  "folder": "D:\\מצבת\\נכנס",
  "baseline_at": "2026-08-17T09:12:03",
  "authorities": { "1400000": "שם:גודל|שם:גודל|…" }
}
```

טביעת האצבע היא **שם + גודל** בלבד, בלי `mtime`: שם הקובץ נושא את חותמת
משרד החינוך ולכן הוא ייחודי לכל עדכון, בעוד `mtime` משתנה בכל העתקה —
וסנכרון שמעתיק את התיקייה כולה מדי חודש היה נראה כמו עדכון של כל
המועצות וגורר טעינה מחדש של אותם נתונים בדיוק.

**מחיקת הקובץ אינה מריצה הכול מחדש** — היא מאפסת את המעקב, ולכן הסבב
הבא ירשום מצב פתיחה חדש ולא יעבד כלום. להרצה בפועל: `--process-existing`.

## גיבוי אוטומטי

הטעינה עושה `TRUNCATE` — הטבלה נמחקת ונטענת מחדש. לכן **לפני כל עדכון**
הסוכן שומר עותק של הטבלה הקיימת, כקובץ אקסל:

```
agent/backups/students_1400000/
├── students_1400000_2026-08-16_2204.xlsx    (5.5MB)
├── students_1400000_2026-09-01_0603.xlsx
└── ...
```

- גיליון אחד, `תלמידים`, עם כל העמודות, מיושר לימין (`sheet_view.rightToLeft`)
  — נפתח ישירות בלחיצה כפולה, בלי שלב פתיחת דחיסה.
- תיקייה נפרדת לכל רשות, כך שמועצה אחת אינה דוחקת את השנייה.
- **טבלה חדשה אינה מגובה** — אין מה לגבות בפעם הראשונה.
- מגבה בכל מסלול: העלאה מהאתר, סריקת התיקייה, והרצה ידנית.

### כמה זמן נשמרים

| כלל | ערך |
|-----|-----|
| גיל מרבי | 90 יום (`BACKUP_MAX_AGE_DAYS`) |
| מספר מרבי | 12 לכל רשות (`BACKUP_KEEP`) |
| חריג | **הגיבוי האחרון לעולם אינו נמחק** |

החריג אינו קוסמטי: אחרי חצי שנה בלי עדכון כל הגיבויים היו עוברים את 90
היום ונמחקים, והעדכון הבא היה דורס את הטבלה בלי שום עותק קודם.

בעדכון חודשי נשמרים בפועל שלושה גיבויים, כ-17MB לרשות.

### שחזור מגיבוי

לפתוח את קובץ האקסל, ולטעון חזרה עם `\copy` מול המסד — או פשוט להשוות
בתוך Excel מה השתנה.

## תקלות נפוצות

| תסמין | פתרון |
|---|---|
| `python לא מותקן` ב-setup | פייתון הותקן בלי `Add Python to PATH` — להתקין מחדש עם הסימון |
| `SELF_SIGNED_CERT` בהתקנה | רשת עם סינון תוכן. `pip install -r requirements.txt --trusted-host pypi.org --trusted-host files.pythonhosted.org` |
| הסטטוס נתקע ב-`בעיבוד` | הסוכן נפל באמצע. לפתוח את `agent.log`, ולהחזיר את השורה ל-`pending` |

| הסוכן לא עולה אחרי הפעלה מחדש | Task Scheduler → לחפש `MatzevetAgent` → לבדוק את `Last Run Result` |

## אבטחה

- `.env.agent` מכיל **סיסמה של חשבון ייעודי**, לא את המפתח הסודי של הפרויקט.
  אם המחשב נפרץ — משהים את החשבון מהאתר וההרשאה נשללת מיד.
  המחשב עדיין צריך להיות בשליטת סבא, עם משתמש נעול בסיסמה.
- קבצי המצב"ת יורדים לתיקייה זמנית ו**נמחקים בסיום העיבוד**, גם כשהוא נכשל.
- הסוכן אינו פותח שום פורט ואינו מקבל חיבורים נכנסים — הוא רק פונה החוצה
  ל-Supabase. אין צורך לפתוח כלום בחומת האש.
