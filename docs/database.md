# מסד הנתונים — סכימה, הרשאות ושדות

מסד הנתונים הוא Supabase (PostgreSQL). המיגרציות נמצאות ב-`supabase/migrations/`.

## טבלאות

### `authorities` — רשויות (מטא)
| עמודה | סוג | תיאור |
|-------|-----|--------|
| code | text (PK) | קוד הרשות, למשל `1400000`. **בלתי ניתן לשינוי** |
| name | text | שם לתצוגה, למשל "מטה מנשה". ניתן לעריכה (מיגרציה 011) |
| moe_code | text | הקוד בשמות קובצי המצב"ת — **אינו בהכרח** `code` (כפר מנדא = 120 אצלנו, 5108 שם). נלמד אוטומטית בעדכון הראשון (מיגרציה 009), **וייחודי** (מיגרציה 015) |
| is_active | boolean | פעילה? השבתה במקום מחיקה |
| created_at | timestamptz | |

מנהל-על רשאי לעדכן (מיגרציה 011), אך **הקוד נעול בטריגר**
`protect_authority_code()` ולא רק בממשק — הוא מרכיב את שם טבלת התלמידים
(`students_{code}`), ושינוי שלו היה מנתק את הרשות מכל נתוניה בשקט.

> ⚠️ **`moe_code` קובע ניתוב, לא רק תיאור.** הסוכן משייך לפיו את הקבצים
> שבתיקייה הנסרקת למועצה שלהם, והטעינה שבסוף המסלול דורסת את הטבלה. שני
> ערכים זהים לשתי מועצות היו יוצרים ניתוב דו-משמעי — ולכן מיגרציה 015
> חוסמת אותם באינדקס ייחודי חלקי (`NULL` מותר: כך נראית מועצה שטרם עודכנה,
> והיא פשוט אינה נסרקת עד שתלמד את הקוד).

### `users` — משתמשים ושיוך לרשויות
| עמודה | סוג | תיאור |
|-------|-----|--------|
| id | uuid (PK) | מקושר ל-`auth.users` |
| email | text | |
| display_name | text | שם לתצוגה |
| role | text | `viewer` / `admin` / `super_admin` |
| authority_codes | text[] | קודי הרשויות שהמשתמש משויך אליהן |
| job_title | text | תפקיד — תיאורי (מיגרציה 010) |
| institution_name | text | שם מוסד — תיאורי (מיגרציה 010) |
| institution_code | text | סמל מוסד — תיאורי (מיגרציה 010) |
| is_service_account | boolean | חשבון מכונה (הסוכן) — מיגרציה 014 |
| can_edit_extra | boolean | רשאי למלא ערכים בעמודות שהמשתמש הוסיף — מיגרציה 016. רלוונטי ל-`viewer` בלבד; `admin` ומעלה רשאי ממילא |

רשומת משתמש נוצרת אוטומטית בעת הרשמה ב-Auth דרך הטריגר `handle_new_auth_user()`,
שקורא `role` ו-`authority_codes` מ-`raw_user_meta_data`.

> ⚠️ שלושת שדות המיגרציה 010 הם **תוויות תצוגה בלבד ואינם משפיעים על
> הרשאות**. ההיקף בפועל נקבע ב-`scope_level`/`scope_values` ונאכף ב-RLS.
> מילוי `institution_code` אינו מגביל את מה שהמשתמש רואה.

### `students_{code}` — טבלת התלמידים (אחת לכל רשות)
- למשל `students_1400000`. **165 עמודות**, מפתח ראשי: `MISPAR_ZEHUT` (תעודת זהות).
- **נדרסת בכל עדכון חודשי** (TRUNCATE + טעינה מחדש).
- שמות העמודות באנגלית (python_name של ה-pipeline); התוויות בעברית ב-`src/config/fields.ts`.
- אינדקסים: על ת.ז. ההורים (זיהוי אחים) ועל סמל מוסד.

### עמודות שהמשתמש מוסיף וטבלאות ייעודיות (מיגרציות 016–020)

| טבלה | תוכן | היקף |
|-------|------|------|
| `extra_columns` | קטלוג העמודות: תווית, סוג (`text`/`checkbox`), סדר, יוצר. `view_id` ריק = עמודה של כל הרשות; מלא = שייכת לטבלה ייעודית אחת | לפי רשות |
| `extra_columns_trash` | עמודות שנמחקו, ל-90 יום. הפיך | לפי רשות |
| `saved_views` | הטבלאות הייעודיות עצמן: שם, תיאור, תמהיל שדות, הסינון שממנו נזרעו (לתיעוד בלבד), ו-`folder_id` | **לפי משתמש** |
| `view_folders` | תיקיות לארגון הסרגל. `parent_id` על עצמה = עץ | **לפי משתמש** |
| `students_{code}_extra` | הערכים. `MISPAR_ZEHUT` + עמודת `jsonb` אחת בשם `data`, שמפתחותיה הם מזהי העמודות | אחת לכל רשות |
| `students_{code}_view_members` | חברוּת מפורשת: איזה ת"ז שייך לאיזו טבלה ייעודית | אחת לכל רשות |

שתי הטבלאות הנלוות נוצרות **בעצלתיים** ב-`ensure_extra_table(code)`,
ונמחקות ב-`delete_authority`.

> **הטבלאות הייעודיות והתיקיות אישיות** (מיגרציה 021): כל המדיניות
> עליהן היא `created_by = auth.uid()` — קריאה, עדכון ומחיקה. משתמש
> אינו רואה את הרשימות של עמיתו, גם לא דרך קריאה ישירה ל-API.
> העמודות שהמשתמש מוסיף (`extra_columns`) **נשארו של הרשות** — הן
> חלק מהטבלה שכולם עובדים עליה. ראה
> [החלטה 011](decisions/011-personal-views-and-folders.md).
>
> מחיקת תיקייה אינה מוחקת טבלאות: `folder_id` היא `on delete set null`,
> והן חוזרות לשורש. טריגר במסד חוסם מעגלים בעץ ותיקיית אב של משתמש אחר.

> ⚠️ **אין מפתח זר** מ-`students_{code}_extra` ל-`students_{code}`.
> זה לא שכחה. מפתח זר היה שובר את ה-`TRUNCATE` של `load_main.py`
> ומשבית את העדכון החודשי; `TRUNCATE ... CASCADE` היה מרוקן בשקט את
> כל מה שהמשתמש הזין. **אל תוסיף אותו.** הקשר נאכף בקריאה, ושורות
> יתומות מסומנות ב-`mark_extra_orphans` ומנוקות בנפרד.

**פונקציות:** `may_manage_extra_columns()` (יצירה/מחיקה — מנהל רשות
ומעלה), `may_edit_extra()` (מילוי ערכים — כולל צופה עם `can_edit_extra`),
`delete_extra_column` / `restore_extra_column` (סל הגריעה),
`extra_column_usage`, `extra_grace_days()` = 90,
`extra_cleanup_preview` / `extra_cleanup_purge` (ניקוי — עדיין בלי
כפתור בממשק), `add_students_to_view`.

**RLS מודע להיקף:** המדיניות על הערכים נבדקת מול הטבלה הראשית
(`exists`), ולא ע"י שכפול `SEMEL_YISHUV1`/`SEMEL_MOSAD` לטבלה
התוספתית — עותק כזה היה מתיישן בעדכון החודשי הבא.

### טבלאות ניהול (מיגרציה 004)

| טבלה | תוכן | מי רואה |
|-------|------|---------|
| `clients` | כרטיס לקוח לכל רשות: איש קשר, מועדי תשלום, חידוש הסכם, עלות | מנהל-על בלבד |
| `client_documents` | מטא-דאטה של מסמכים; הקובץ עצמו ב-Storage | מנהל-על בלבד |
| `moe_uploads` | תור העלאות: ממתין / בעיבוד / הושלם / נכשל | מנהל-על, או משתמש ברשות שלו |

### הרשאות ברמת המשתמש

| עמודה ב-`users` | ערכים | תפקיד |
|------------------|--------|-------|
| `role` | `viewer` / `admin` / `super_admin` | מה מותר לעשות |
| `scope_level` | `council` / `locality` / `school` | **אילו תלמידים** נראים |
| `scope_values` | `text[]` | סמלי היישובים או המוסדות המותרים |
| `is_suspended` | boolean | מושהה — חסום בכניסה ובנתונים |
| `can_edit_extra` | boolean | האם צופה רשאי למלא **ערכים** בעמודות תוספתיות. אינו מתיר ליצור עמודות, ואינו מרחיב את ההיקף |

### פונקציות עזר

| פונקציה | מחזירה |
|----------|---------|
| `has_authority(code)` | האם המשתמש משויך לרשות. **מנהל-על → תמיד true** (מיגרציה 008) |
| `in_user_scope(yishuv, mosad)` | האם השורה בטווח ההיקף של המשתמש |
| `is_super_admin()` | האם מנהל-על ואינו מושהה |
| `create_authority(code, name)` | יוצרת רשות + טבלה + RLS. מנהל-על בלבד |
| `may_update_moe(code)` | האם רשאי **להעלות** מצב"ת — `admin` ברשות שלו או מנהל-על (מיגרציה 012) |

הפונקציות המחזירות בוליאני מחזירות `false` למשתמש מושהה.

## הרשאות (RLS)
- **`students_{code}`**: שתי בדיקות מצטברות —
  ```sql
  using (has_authority('{code}') and in_user_scope("SEMEL_YISHUV1", "SEMEL_MOSAD"))
  ```
  השיוך לרשות *וגם* ההיקף בתוכה. ההיקף רק מצמצם, לעולם לא מרחיב.
- **`users`**: כל משתמש קורא רק את הרשומה של עצמו.
- **`authorities`**: כל משתמש מאומת יכול לקרוא; **עדכון — מנהל-על בלבד**
  (מיגרציה 011), והקוד נעול בטריגר.
- **`moe_uploads`**: קריאה לכל מי שמשויך לרשות; **כתיבה — `may_update_moe`
  בלבד** (מיגרציה 012).

## שדות מחושבים

ארבעה שדות אינם מגיעים ישירות ממשרד החינוך. הראשון מחושב **בטעינה**
ונשמר בעמודה; שלושת הנותרים מחושבים **בדפדפן** בכל טעינת נתונים
([`lib/computed.ts`](../src/lib/computed.ts)) ואינם קיימים כעמודות ב-DB.

| שדה | היכן מחושב | לוגיקה |
|------|-------------|---------|
| `KITA_MESHULEVET` (כיתה משולב) | טעינה (Python) | מ"מקבילה": ט5 → ט-5 |
| `STATUS_CHINUCH_MEYUCHAD` | דפדפן | סוג חינוך מוסד ≠ "רגיל" → **מוסד**; אחרת סוג כיתה שאינו רגיל → **כיתה** |
| `STATUS_TALMID_BARASHUT` | דפדפן | רשות המוסד = רשות המגורים → **תלמיד ברשות** / **תלמיד חוץ** |
| `SEMEL_MASLUL` (סמל מסלול) | דפדפן | מיפוי הפוך של `CODE_MASLUL` מטקסט לקוד |

**"לב טכנולוגי" ו"לב עיוני" אינם חינוך מיוחד** למרות שסוג הכיתה שלהם אינו
"רגילה". ההשוואה מנרמלת גרשיים (`"` `'` `״` `׳`) ורווחים כפולים לפני
הבדיקה — בלעדי זה הכללים לא נתפסים.

> **למה בדפדפן ולא בשרת:** שני הסטטוסים נגזרים מעמודות שכבר נטענו, בלי
> מקור נתונים נוסף. חישוב בצד הלקוח חסך שינוי ב-pipeline של סבא ובכל
> טבלאות הרשויות. הנימוק המלא: [decisions/007](decisions/007-client-side-features.md).

## אחסון (Storage) — מיגרציה 005

שני באקטים, שניהם **פרטיים**. הצפייה רק דרך signed URL זמני.

| באקט | תוכן | גישה |
|-------|------|------|
| `client-documents` | חוזים, חשבוניות ואישורים | מנהל-על בלבד |
| `moe-uploads` | קבצי מצב"ת שהועלו, לפי `{code}/{timestamp}/` | קריאה: לפי שיוך · כתיבה: מנהל רשות |

ב-`moe-uploads` החלק הראשון בנתיב הוא קוד הרשות. הקריאה נבדקת מול
`has_authority`, ו**הכתיבה מול `may_update_moe`** (מיגרציה 012).

## יומן פעולות ניהול — `admin_audit` (מיגרציה 014)

נכתב **בטריגר בלבד**, על `users` ועל `authorities`. כל יצירה, עדכון
ומחיקה נרשמת: מתי, על מי, מה השתנה (`לפני` → `אחרי` לכל עמודה), ומי
ביצע.

| עמודה | תוכן |
|-------|------|
| `actor_id` / `actor_email` | מי ביצע. המייל משוכפל בכוונה — הוא שורד את מחיקת המבצע |
| `via` | `user` (JWT של משתמש) · `service_role` · `direct` (חיבור ישיר למסד) |
| `changes` | ב-`update` רק העמודות שהשתנו; ב-`insert`/`delete` השורה המלאה |

**היומן אינו ניתן לעריכה.** יש מדיניות `SELECT` למנהל-על, ו**אין
מדיניות כתיבה כלל** — הטריגר הוא `security definer` ועוקף RLS, ולכן גם
מנהל-על אינו יכול לשכתב דרך ה-API. אומת: `DELETE` ו-`UPDATE` נוגעים
ב-0 שורות, `INSERT` נדחה מפורשות.

> ⚠️ **המבצע אינו ידוע בפעולות שעוברות ב-Edge Function.** יצירת משתמש,
> קביעת סיסמה, השהיה ומחיקה רצות עם `service_role`, שאין בו `sub` — הן
> נרשמות עם `via='service_role'` ובלי מבצע. שינוי תפקיד והיקף, שעוברים
> ישירות ל-PostgREST עם ה-JWT של המשתמש, **כן** מתועדים בשמו. השלמת
> הפער דורשת פריסה מחדש של `admin-users` כך שתרשום את המבצע שהיא כבר
> מזהה.

> ℹ️ `auth.audit_log_entries` של Supabase קיימת בפרויקט אך **ריקה**, ולכן
> אי אפשר להישען עליה.

## הגנה על מנהל-העל האחרון (מיגרציה 014)

טריגר `before update or delete` על `users` חוסם שלוש דרכים להישאר בלי
מנהל: **מחיקה**, **השהיה**, ו**הורדת תפקיד** — של האחרון שנשאר.

`agent@matzevet.local` מסומן `is_service_account` ו**אינו נספר**. בלי
זה אפשר היה למחוק את כל בני האדם, המערכת הייתה נראית תקינה, ואיש לא
היה יכול להיכנס ולתקן.

> ההגנה יושבת בטריגר ולא ב-Edge Function כי המחיקה מגיעה בפועל
> **בשרשור מ-`auth.users`**. בטריגר היא תופסת בכל מסלול.
