# עמודות שהמשתמש מוסיף — אפיון תשתית

אפיון + מצב מימוש. שכבת המסד מומשה ב-[מיגרציה 016](../supabase/migrations/016_extra_columns.sql);
צד הלקוח טרם נבנה. **המיגרציה טרם הורצה על המסד החי.**

> **מחליף את הגרסה הקודמת של המסמך**, שאפיינה רשימת שדות **קבועה**
> (42 עמודות מ-`Additional_fields_11.xlsx`) שסבא היה מאשר מראש. הדרישה
> החדשה היא שהמשתמש עצמו יוסיף עמודות מתי שירצה — ולכן רשימה קבועה
> אינה פתרון, אלא בדיוק הדבר שצריך להיעלם.

## הצורך

שני פיצ'רים שהתבררו כאותו מנגנון:

1. **עמודות שהמשתמש מוסיף** — טקסט, ותיבת סימון לסימון תלמידים
   ("זכאי הסעה", "טופל", "הערה"). אסור שיידרסו בעדכון החודשי.
2. **מסכים ייעודיים** — תת-טבלה מסוננת עם עמודות משלה. למשל
   "הסעות ליישוב מצר": תלמידי מצר בלבד, ועליהם שלוש עמודות ניהול.

**פיצ'ר 2 הוא פיצ'ר 1 בתוספת סינון שמור.** אין שתי מערכות אחסון —
עמודה של מסך ייעודי היא עמודה רגילה שמשויכת למסך אחד במקום לרשות כולה.

## ההחלטה: עמודה היא **נתון**, לא **סכימה**

הרעיון הראשוני היה טבלה נוספת לכל מועצה, שבה כל עמודה שהמשתמש מוסיף
היא עמודה אמיתית ב-Postgres. הכיוון נכון — טבלה נפרדת שאינה נדרסת — אבל
הוא גורר `ALTER TABLE` בזמן ריצה מהדפדפן, וזו שרשרת בעיות:

| | עמודות אמיתיות (DDL) | קטלוג + JSONB |
|---|---|---|
| הוספת עמודה | `ALTER TABLE` + `NOTIFY pgrst, 'reload schema'` | שורה בקטלוג |
| מחיקת עמודה | `DROP COLUMN` — הנתונים אבודים מיידית | `is_archived`, הפיך |
| שם העמודה | חייב חיטוי מלא — הוא נכנס ל-SQL | מזהה שהמערכת מייצרת; השם הוא תווית |
| סכימה בין מועצות | מתפצלת — לכל רשות עמודות אחרות | זהה לכולן לנצח |
| מי מורשה | DDL מחייב `security definer` שכותב סכימה | הרשאת `INSERT` רגילה |
| תקרה | 1600 עמודות לטבלה | אין |

**מה שהכריע:** DDL מהדפדפן הוא בדיוק משפחת הבאגים שכבר עלתה לנו —
פעולה שנראית תמימה, מצליחה בשקט, ומשנה מבנה שכל השאר תלוי בו
(מיגרציה 011 על קוד הרשות, מיגרציה 015 על `moe_code`). מחיקת עמודה
בטעות בדפדפן מוחקת נתונים של כל תלמידי הרשות בלי דרך חזרה.

לכן: **טבלה אחת לכל רשות עם עמודת `jsonb` אחת**, וקטלוג נפרד שמגדיר
מה יושב בתוכה.

## הסכימה

```sql
-- ── הקטלוג: אילו עמודות קיימות. משותף לרשויות, מסונן ב-RLS ──
create table public.extra_columns (
  id             uuid primary key default gen_random_uuid(),
  authority_code text not null references public.authorities(code) on delete cascade,
  -- null = עמודה של הרשות כולה. אחרת — שייכת למסך ייעודי אחד בלבד.
  view_id        uuid references public.saved_views(id) on delete cascade,
  label          text not null,                      -- מה שהמשתמש רואה
  type           text not null check (type in ('text', 'checkbox')),
  position       int  not null default 0,
  is_archived    boolean not null default false,     -- מחיקה הפיכה
  created_by     uuid references public.users(id),
  created_at     timestamptz not null default now()
);

-- ── האחסון: שורה לתלמיד, טבלה לכל רשות. אינה נדרסת לעולם ──
create table public.students_{code}_extra (
  "MISPAR_ZEHUT" text primary key,
  data           jsonb not null default '{}',   -- { "<extra_columns.id>": value }
  updated_at     timestamptz not null default now(),
  updated_by     uuid references public.users(id)
);
```

**המפתח ב-`data` הוא ה-id של העמודה ולא השם.** שינוי שם עמודה הוא
עדכון תווית בקטלוג, ולא הגירת נתונים.

**תלמיד בלי נתונים תוספתיים — אין לו שורה בכלל.** אין יצירה מראש של
8,000 שורות ריקות; השורה נוצרת ב-`upsert` בסימון הראשון.

### אין צורך באינדקס על `data`

הסינון רץ בצד הלקוח על המערך שכבר בזיכרון
([001](decisions/001-tech-choices.md)), ולכן אין שאילתה שמסננת לפי
עמודה תוספתית. אינדקס GIN יידרש רק אם הסינון יעבור לצד השרת.

## איך זה שורד את העדכון החודשי

**אפס שינויים בסוכן ואפס שינויים ב-pipeline.**

הטעינה עושה `TRUNCATE students_{code}` — טבלה אחרת לגמרי.
`students_{code}_extra` פשוט אינה מעורבת. אין דלתא, אין סנכרון, ואין
קוד חדש שרץ על השרת.

> האפיון הקודם דרש עדכון דלתא בסוכן — מחיקת מי שנגרע והוספת מי שנוסף,
> מיד אחרי כל טעינה. זהו שינוי בשרת, והוא גם מסוכן. ראה למטה.

## מחיקת עמודה — סל גריעה, ואז מחיקה סופית

**`extra_columns` מכילה אך ורק עמודות חיות.** אין דגל `is_archived`, ואין
תנאי סינון בשום שאילתה — עמודה או שקיימת או שלא. מחיקה מעבירה את השורה
ל-`extra_columns_trash`, ושחזור מחזיר אותה. אותו `id` נשמר.

**הערכים אינם זזים.** הם נשארים ב-`data` תחת אותו מפתח, בלי שאיש מציג
אותם. לכן מחיקה ושחזור הן העברת שורה אחת, גם בעמודה עם ערכים לאלפי
תלמידים. רק המחיקה הסופית, אחרי 90 יום, נוגעת בשורות התלמידים.

> **למה טבלה נפרדת ולא דגל:** דגל היה הופך "עמודה קיימת אבל מוסתרת"
> למצב שכל מסלול הקריאה חייב להכיר — רישום השדות, בורר השדות, הייצוא,
> המסכים הייעודיים. הסיבוך היה מתפזר על כל הקריאות. כאן הוא יושב כולו
> בשתי פעולות נדירות.

**ההגנה המרכזית אינה סל הגריעה אלא `extra_column_usage()`**, שנקראת
לפני אישור המחיקה ומחזירה כמה תלמידים מחזיקים ערך בעמודה. הטעות הנפוצה
היא "חשבתי שהעמודה לא בשימוש", והמספר עונה עליה בנקודה שבה היא נוצרת.
סל הגריעה מטפל במה שנשאר.

## ניקוי שורות יתומות — כן, אבל לא בזמן הטעינה

שורה יתומה היא שורה תוספתית של תלמיד שכבר אינו במצב"ת. **צריך למחוק
אותן** — ולא בגלל נפח (שורה עולה כמה בייטים), אלא מסיבה חזקה יותר:
היא מחזיקה **תעודת זהות של קטין שכבר אינו ברשות**, ולצדה מה שנכתב
עליו — הערה רפואית, זכאות, סימון. זהו בדיוק סוג המידע שאין סיבה
להחזיק אחרי שהילד עזב.

הטיעון ההפוך — *"אולי הוא יחזור והנתונים יחכו לו"* — חלש. תלמיד שעוזב
מועצה בדרך כלל אינו חוזר, ולבנות סביב המקרה הנדיר הזה זו הצדקה
לשמירת מידע שלא צריך להישמר.

### אבל המחיקה אסור שתרוץ בעקבות הטעינה

זו הנקודה הקריטית, והיא **לא** על נוחות. "מחק כל שורה תוספתית שאין לה
ת"ז בטבלה הראשית", כשהיא רצה מיד אחרי `TRUNCATE` + טעינה מחדש, הופכת
כל טעינה שגויה לאובדן בלתי הפיך.

זה לא תרחיש תיאורטי. ב-[005](decisions/005-watch-folder-baseline.md)
נטענו בטעות קובצי מטה מנשה לטבלה של כפר מנדא — **0 תעודות זהות
משותפות** בין מה שהיה למה שנטען. הטבלה הראשית שוחזרה מהגיבוי שהסוכן
לקח רגע קודם. אילו ניקוי יתומים היה רץ אוטומטית באותו רגע, הוא היה
מוחק **100% מהנתונים התוספתיים של אותה רשות** — ולטבלה התוספתית אין
גיבוי.

כלומר: ניקוי אוטומטי צמוד לטעינה הופך תקלה שניתנת לשחזור לתקלה שאינה
ניתנת לשחזור.

### הפתרון: סימון, תקופת חסד, ואז מחיקה

שני שלבים שמופרדים בזמן מהטעינה:

```sql
-- מתווסף לטבלה התוספתית
orphaned_at timestamptz    -- null = התלמיד קיים במצב"ת
```

**סימון** (זול, אפשר להריץ בכל תדירות):

- שורה שאין לה ת"ז בטבלה הראשית ו-`orphaned_at is null` → `orphaned_at = now()`
- שורה שיש לה ת"ז בטבלה הראשית ו-`orphaned_at is not null` → `orphaned_at = null`

**הסעיף השני הוא מה שמרפא את עצמו:** בטעינה שגויה כל השורות מסומנות,
אבל אף אחת לא נמחקת. בעדכון הבא, כשהנתונים הנכונים חוזרים, הסימון
מתבטל מעצמו. אף אחד לא צריך לשים לב ולתקן.

**מחיקה** — רק שורות שמסומנות יותר מ-**90 יום**.

התקרה נבחרה כדי להתיישר עם `BACKUP_MAX_AGE_DAYS` בסוכן: זהו ממילא
החלון שבו אפשר לשחזר את הטבלה הראשית. מעבר לו אין רשת ביטחון בשום
מקרה, ולכן אין טעם להחזיק את היתומים יותר.

### איפה זה רץ

**לא בסוכן.** שתי אפשרויות, ואפשר גם שתיהן:

1. **פעולה במסך הניהול** — מציגה כמה שורות מסומנות וכמה עומדות
   להימחק, **לפני** שהיא מוחקת. תמיד זמינה.
2. **`pg_cron` ב-Supabase** — הרצה חודשית, לגמרי בתוך המסד.
   *(יש לוודא שההרחבה זמינה בפרויקט לפני שמסתמכים עליה.)*

בשתי הדרכים הסוכן אינו יודע שהמנגנון קיים.

### שלושת התנאים שמחזיקים את זה

הסוכן נוגע ב-`students_{code}` **בלבד** — יצירה מהתבנית (`ensure_table`),
`COPY` לגיבוי, `count`, ו-`truncate` ב-`load_main.py`. אי-הנגיעה בטבלה
התוספתית אינה מקרית; היא נשענת על שלוש החלטות, וכל אחת מהן שתישבר
תחזיר את השינוי לשרת:

1. **אין מפתח זר מהטבלה התוספתית לטבלה הראשית.** `MISPAR_ZEHUT` הוא
   `text primary key` ותו לא. ⚠️ **זו המלכודת המסוכנת ביותר כאן:**
   `references students_{code}("MISPAR_ZEHUT")` נראה כמו הדבר הנכון
   לעשות, אבל הוא גורם ל-`truncate table public.students_{code}` להיכשל
   (`cannot truncate a table referenced in a foreign key constraint`) —
   כלומר **העדכון החודשי של אותה רשות מפסיק לעבוד**. והתיקון שאליו
   מושכת האינטואיציה, `TRUNCATE ... CASCADE`, מרוקן בשקט את הטבלה
   התוספתית — בדיוק הנתונים שהפיצ'ר נועד להגן עליהם.
   היושרה נשמרת אפליקטיבית ובניקוי היתומים, לא באילוץ.
2. **הטבלה התוספתית נוצרת בעצלות מהאתר**, ולא ב-`ensure_table` של
   הסוכן ולא ב-`create_authority`.
3. **הניקוי מנותק מהטעינה.** אין סנכרון דלתא בעקבות `load_main.py`;
   היתומים מסומנים ונמחקים אחרי תקופת חסד, במסלול נפרד.

### פער ידוע: הטבלה התוספתית אינה מגובה

`backup_table` מגבה את `students_{code}` בלבד, כי היא זו שעומדת
להידרס. הטבלה התוספתית אינה נדרסת על ידי שום תהליך אוטומטי, ולכן
פרופיל הסיכון שלה שונה — טעות אנוש ולא דריסה מתוזמנת. הארכוב ההפיך
של עמודה מכסה את התרחיש הגרוע ביותר (מחיקת עמודה), אבל **לא** עריכה
המונית של ערכים. גיבוי תקופתי שווה שקילה בהמשך — כייצוא מתוזמן, ולא
כתוספת לסוכן.

### יצירת הטבלה — עצלה, ולא במסלול היצירה

`create_authority` ([006](../supabase/migrations/006_create_authority.sql))
יוצרת מועצה, אבל **הסוכן יוצר טבלאות בעצמו** (`ensure_table` ב-`worker.py`)
כשמגיעים קבצים של מועצה שאינה במערכת. שני מסלולים — ואם נוסיף את
הטבלה התוספתית רק לאחד, למועצות מהמסלול השני היא לא תיווצר, בשקט.

לכן `ensure_extra_table(code)`: פונקציית `security definer` אידמפוטנטית
שנקראת מהאתר בפעם הראשונה שמישהו מוסיף עמודה. שני המסלולים מתכנסים
אליה, והיא מרפאת גם מועצות שכבר קיימות.

`delete_authority` ([013](../supabase/migrations/013_delete_authority.sql))
כן צריכה `drop table if exists students_{code}_extra` — אחרת נשארת
טבלה יתומה עם תעודות זהות, בדיוק התרחיש שהמיגרציה ההיא באה למנוע.

## הרשאות

שלוש רמות, ולא אחת:

| פעולה | מי |
|--------|-----|
| **יצירת/מחיקת עמודה** | `admin` או `super_admin` — **בכל רמת היקף** (מועצתי, יישובי, בית-ספרי) |
| **עריכת ערכים** | `admin`, או `viewer` שהוענק לו `can_edit_extra` |
| **צפייה** | כל מי שרואה את התלמיד |
| **ניקוי סופי** | `admin` ומעלה — פעולת תחזוקה, לא פעולת עבודה |

> **צופה אינו יוצר עמודות.** [מיגרציה 018](../supabase/migrations/018_open_extra_columns.sql)
> פתחה זאת לכל משתמש ובוטלה ב-[019](../supabase/migrations/019_revert_open_columns.sql).
> ההגבלה היא לפי **תפקיד** ולא לפי היקף: מנהל בית ספר יוצר עמודות בדיוק
> כמו מנהל מועצתי.

סבא (13.8): *"אולי לייצר איזושהי הרשאת עריכה, שיש כאלה שאפשר להגדיר
להם אותם רק לצפייה."* לכן `can_edit_extra` הוא דגל נפרד ולא נגזרת של
`role` — מזכירה צריכה לערוך בלי להיות מנהלת רשות.

### ה-RLS חייב לכבד גם את ההיקף

`students_{code}_extra` אינה מכילה `SEMEL_YISHUV1`/`SEMEL_MOSAD`, ולכן
`in_user_scope` אינה יכולה לפעול עליה ישירות. שתי דרכים:

1. **לשכפל את שני הסמלים לשורה התוספתית** — מהיר, אבל **מתיישן**:
   תלמיד שעבר מוסד משאיר שורה עם המוסד הישן, ומשתמש בית-ספרי שכבר
   אינו אמור לגעת בו — יכול. נדחה.
2. **`exists` מול הטבלה הראשית** — הנבחר. שם הטבלה ידוע בזמן יצירת
   המדיניות, ולכן אפשר להטמיע אותו:

```sql
create policy students_{code}_extra_read on public.students_{code}_extra
  for select to authenticated
  using (
    public.has_authority('{code}')
    and exists (
      select 1 from public.students_{code} s
       where s."MISPAR_ZEHUT" = public.students_{code}_extra."MISPAR_ZEHUT"
         and public.in_user_scope(s."SEMEL_YISHUV1", s."SEMEL_MOSAD"))
  );
-- הכתיבה: אותו תנאי, ובנוסף public.may_edit_extra('{code}')
```

ה-`exists` רץ מול המפתח הראשי — סריקת אינדקס, לא סריקת טבלה.
ה-RLS של הטבלה הראשית חלה גם על תת-השאילתה, כך שההגנה כפולה;
`in_user_scope` נכתב במפורש בכל זאת, כדי שהמדיניות תעמוד בפני עצמה.

> **מדיניות כתיבה נפרדת ממדיניות קריאה**, בכוונה. צפייה אינה עריכה —
> בלי ההפרדה חוזרים בדיוק לפרצה של [מיגרציה 012](../supabase/migrations/012_restrict_moe_upload.sql):
> הסתרה בתצוגה שאינה הרשאה.

### עמודה שקיימת רק בטבלה ייעודית אחת

`extra_columns.view_id` קובע היכן העמודה מופיעה:

| `view_id` | היכן |
|---|---|
| `null` | בכל הרשות — הטבלה הראשית וכל המסכים |
| מזהה טבלה ייעודית | **רק** בתוכה |

כשמוסיפים עמודה מתוך טבלה ייעודית, הטופס שואל היכן היא תופיע, וברירת
המחדל היא **רק כאן**. "קו הסעה" חסרת משמעות אצל 7,900 תלמידים שאינם
ברשימה, והוספתה לכולם רק מנפחת את בורר השדות ואת הייצוא.

`fetchExtraColumns(code, viewId)` מסננת בהתאם. **הסינון הזה אינו
קוסמטי** — בלעדיו כל עמודה של טבלה ייעודית הייתה דולפת לטבלה הראשית.

מחיקת טבלה ייעודית גוררת את העמודות ששייכות רק לה (`on delete cascade`),
ואינה נוגעת בעמודות הרשות.

## פיצ'ר 2 — מסכים ייעודיים

```sql
create table public.saved_views (
  id             uuid primary key default gen_random_uuid(),
  authority_code text not null references public.authorities(code) on delete cascade,
  name           text not null,                  -- "הסעות — מצר"
  description    text,
  base_preset    text,                           -- מאיזו תצורה נפתח
  filters        jsonb not null default '[]',    -- FilterCondition[] — אותו מבנה בדיוק
  fields         text[] not null default '{}',   -- מפתחות עמודות, לפי הסדר
  sort           jsonb,
  visibility     text not null default 'authority'
                 check (visibility in ('private', 'authority')),
  created_by     uuid references public.users(id),
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);
```

`filters` נשמר **באותו מבנה** שהטבלה כבר מייצרת, ושהניווט לפיבוט כבר
מעביר ב-`state` של הראוטר ([007](decisions/007-client-side-features.md)).
אין פורמט חדש ואין המרה — מסך ייעודי הוא צילום של מצב שהמשתמש כבר
יודע להגיע אליו בעצמו.

**ברירת המחדל היא `authority` ולא `private`:** "טבלת ההסעות של מצר" היא
נכס של הרשות, לא של מי שיצר אותה. משתמש שעוזב לא לוקח אותה איתו.

### חברוּת מפורשת, ולא סינון שמחושב מחדש

**זו ההכרעה המרכזית של הפיצ'ר.** טבלה ייעודית מחזיקה **רשימת תעודות
זהות** ב-`students_{code}_view_members` ([מיגרציה 017](../supabase/migrations/017_view_members.sql)),
ולא תנאי שמורץ בכל פתיחה.

מה שהכריע: הדרישה "להגיע לסינון באחד המסכים ואת מי שסיננת להוסיף לאחת
הטבלאות". פעולה כזו אפשרית רק כשהחברוּת מפורשת — בסינון דינמי היית
עורך את התנאי, לא "מוסיף אנשים".

`saved_views.filters` נשמר כ**תיעוד** של הסינון שממנו נזרעה הרשימה, כדי
שאפשר יהיה לענות בעוד חצי שנה "מאיפה הגיעו 47 האלה". הוא אינו מורץ מחדש.

**המחיר, וחייב להיות גלוי במסך:** תלמיד חדש שמתאים לסינון המקורי אינו
מצטרף מעצמו, ותלמיד שיצא מהסינון נשאר עד שיוסר. ההודעה הזו מופיעה
בחלון היצירה ובבאנר של הרשימה — לא כהערת שוליים.

### ההיקף גובר על הרשימה

רשימה משותפת שנבנתה על יישוב אחד עדיין עוברת דרך ה-RLS: משתמש בית-ספרי
שייכנס אליה יראה רק את תלמידי המוסד שלו. הרשימה מצמצמת, לעולם לא
מרחיבה — כמו `scope_values`.

ההוספה עוברת ב-`add_students_to_view()`, שמסננת את הת"ז מול הטבלה
הראשית: אי אפשר לתחוב לרשימה מישהו שאינו ברשות, גם לא בקריאה ישירה
ל-API. הפונקציה מדלגת על מי שכבר ברשימה ומחזירה כמה **באמת** נוספו.

## מה משתנה בצד הלקוח

**11 קבצים קוראים ל-`getField` / `fieldLabel` / `ALL_FIELDS`** —
`filters.ts`, `table.ts`, `exportExcel.ts`, `FilterBar`, `FieldPicker`,
`FieldCombobox`, `StudentTable`, `StudentCard`, `Dashboard`, `Pivot`.
העברת רשימת שדות דינמית דרך context הייתה נוגעת בכולם.

**במקום זה — רישום ברמת המודול** ב-`config/fields.ts`, באותו דפוס של
המטמון ב-`lib/students.ts`:

```ts
registerExtraFields(defs)   // בהחלפת רשות
clearExtraFields()
```

`getField` ו-`fieldLabel` ממשיכים לעבוד כמו שהם; `ALL_FIELDS` הופך
ל-getter. אפס שינוי ב-10 מתוך 11 הקבצים.

**מפתח העמודה הוא `x_<uuid>`** — אינו מתנגש בשום שם עמודה של משרד
החינוך. שדה שאינו רשום מחזיר `undefined` מ-`getField`, וכל המנועים
נופלים ל-`text` — כלומר עמודה שאורכבה אינה מפילה מסך שמור, רק מוצגת
כטקסט.

### `type: 'boolean'` — התוספת האמיתית היחידה למנועים

היום `FieldType = 'text' | 'number' | 'date'`. תיבת סימון דורשת:

- `filters.ts` — טיפוס `boolean` ואופרטורים `מסומן` / `אינו מסומן`
  (ולא `equals` עם `"true"` — המשתמש אינו אמור להקליד ערך).
- `columnValues.ts` — התוויות `מסומן` / `לא מסומן` במקום `true`/`false`.
- `StudentTable` — תא שהוא `<input type="checkbox">` ולא טקסט, ועריכה
  במקום כשיש הרשאה.
- `xlsx.ts` — `✓` או ריק. **לא** `TRUE`/`FALSE` באנגלית.

**הפיבוטים מקבלים את זה בחינם.** ברגע שעמודה תוספתית נמצאת
ב-`ALL_FIELDS`, "כמה תלמידים סומנו כזכאי הסעה, לפי יישוב" הוא פיבוט
קיים עם ציר אחר.
